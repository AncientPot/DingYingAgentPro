智能Agent平台重构设计需求文档

总体架构设计
架构模式：前后端分离 (B/S 架构)
    前端：SPA 单页应用（推荐 Vue3/React），负责交互、配置界面、流式响应渲染。
    后端：RESTful API + WebSocket/SSE（用于流式传输），负责业务逻辑、LangGraph 编排、工具运行时、配置持久化。
核心原则：
    配置即数据：所有可变配置（提示词、工具开关、模型参数）必须落库/落盘，禁止仅存于内存。
    会话隔离：每个 Session 拥有独立的配置上下文，互不干扰。
    热插拔：工具加载与配置修改无需重启服务，实时生效。

模块化后端设计规范
为了解决当前代码中逻辑耦合的问题，后端需拆分为以下独立模块：
模块名称   职责描述   关键接口/功能
Config Manager   全局与会话级配置的读写、校验、持久化   get_session_config, update_global_settings, validate_schema

Tool Registry   动态扫描、加载、卸载工具；维护工具元数据   scan_tools_dir, enable/disable_tool, get_active_tools

Agent Core   LangGraph 图构建、状态管理、运行时注入   build_graph(config), stream_chat, invoke

Session Store   会话生命周期管理、历史消息存储、配置绑定   create_session, delete_session, bind_config

LLM Provider   多模型适配、API Key 管理、Token 统计   get_model_instance, switch_model

核心功能需求详解

3.1 动态工具系统（重点）
针对您“自定义Python文件自动导入”的需求，设计如下机制：

约定式目录结构：
        /custom_tools
      ├── init.py
      ├── my_calculator.py      # 用户自定义工具
      └── netease_controller.py # 用户自定义工具

工具编写规范：
    文件内必须包含使用 @tool 装饰器的函数。
    函数必须包含标准的 Google/NumPy 风格 Docstring（作为 AI 的工具描述）。
    支持 requirements.txt 或文件头注释声明依赖，便于环境检查。
动态加载器 (Tool Loader)：
    启动时扫描：遍历 /custom_tools，使用 importlib 动态导入，解析 @tool 对象注册到 ToolRegistry。
    运行时热重载：提供 API /api/tools/reload，监听文件变化或手动触发，重新扫描并更新内存中的工具列表。
    安全沙箱：考虑到工具涉及本地操作（如您的网易云控制），需在配置中标记“信任级别”，高危工具需二次确认。
会话级工具绑定：
    工具不再全局写死在 tools = [...] 中。
    每次对话请求时，根据当前 Session Config 中的 enabled_tools 列表，从 ToolRegistry 动态组装工具集传入 LangGraph。

3.2 会话级独立配置与实时生效
配置模型设计：
        {
      "session_id": "uuid",
      "system_prompt": "你是一个专注于音乐的助手...",
      "model_config": { "model_name": "deepseek-chat", "temperature": 0.7 },
      "enabled_tools": ["control_netease_cloud_music", "calculator"],
      "updated_at": "2023-10-27T10:00:00Z"
    }

实时生效机制：
    前端修改配置 -> 调用 PUT API -> 后端写入 DB/JSON -> 返回成功。
    关键点：LangGraph 的 dingyingagent 节点不应在初始化时绑定配置，而应在 每次 invoke/stream 时 从 State 或 Config 参数中读取最新配置。
    代码改造示例：llm.bind_tools(tools) 应改为在节点函数内部执行，tools 来源于当前请求上下文。

3.3 数据一致性与本地持久化
存储策略：
    结构化数据（会话列表、配置、用户设置）：继续使用 SQLite 或迁移至 PostgreSQL，保证事务完整性。
    非结构化数据（长文本Prompt、复杂JSON配置）：可存 DB 的 JSON 字段，或独立 JSON 文件（通过 DB 记录路径和哈希值校验）。
一致性保障：
    单一事实来源 (SSOT)：后端数据库/文件为唯一真理源。前端仅作为展示层，所有修改必须经后端 API 确认后才更新 UI 状态。
    乐观锁/版本号：配置表增加 version 字段，防止并发修改覆盖。
    原子操作：会话创建/删除/配置更新必须在同一个数据库事务中完成，避免出现“会话存在但配置丢失”的孤儿数据。

3.4 全局设置与模型管理
全局配置：独立于会话，存储在 global_settings 表中。包括默认模型、API Keys、代理设置、工具扫描路径等。
继承与覆盖：会话配置优先；若会话未指定某项（如 model），则 fallback 到全局配置。
敏感信息保护：API Key 在后端加密存储，前端仅显示掩码，传输过程全链路 HTTPS。

前端交互设计要求
配置面板：
    侧边栏或弹窗形式，支持 Markdown 编辑系统提示词。
    工具列表采用 Toggle Switch，切换后立即调用保存接口，并给出“已生效”反馈。
    模型选择下拉框，支持从后端获取可用模型列表。
对话界面：
    支持 SSE/WebSocket 流式输出。
    工具调用过程可视化（显示工具名、参数、返回值、耗时）。
    会话切换时，自动拉取该会话的最新配置并刷新界面状态。
状态同步指示器：
    当配置保存中/失败时，UI 应有明确状态提示，避免用户误以为已生效。

迁移与实施路线图建议
Phase 1: 后端重构与API化
    剥离 CLI 交互逻辑，封装 FastAPI/Flask 服务。
    实现 ToolRegistry 和动态加载器。
    重构 LangGraph 图，使其支持运行时配置注入。
    实现配置持久化与一致性校验逻辑。
Phase 2: 前端开发与联调
    搭建基础框架，实现会话管理与对话流式渲染。
    开发配置面板，对接后端 CRUD API。
    实现工具开关与提示词编辑的实时反馈。
Phase 3: 高级特性与优化
    工具热重载与依赖检查。
    配置版本历史与回滚。
    性能优化（工具扫描缓存、连接池）。

对现有代码的具体改造点
移除硬编码：删除 tools = [search, calculator, ...] 和 system_prompt = SystemMessage(...) 的全局定义。
State 扩展：在 State TypedDict 中增加 config 字段，或在 graph.stream() 的 config 参数中传递会话级配置。
工具函数解耦：将 control_netease_cloud_music 等函数移至 /custom_tools 目录，保持主程序纯净。
会话管理升级：将 sessions.json 的逻辑迁移至数据库表，增加 config 列或关联表，确保配置与会话强绑定。

此文档可作为您后续开发的技术蓝图。它既保留了您原有代码的核心能力（LangGraph、本地工具控制），又系统性地解决了扩展性和工程化问题。建议您优先实现 Phase 1 中的动态工具加载和配置注入，这是满足您“随开随生效”和“自定义工具导入”需求的关键基石。
